## Git と GitHub

| 名前 | 何か | どこにあるか |
| --- | --- | --- |
| Git | ファイルの変更の記録（履歴）をとるソフト | 自分の PC に入れて使う |
| GitHub | Git の記録をインターネット上に置いて、ほかの人と共有する Web サービス | インターネット上（github.com） |

- **commit・push・pull** は Git の機能です。VS Code のターミナル（またはボタン）で行います。
- **PR・レビュー・Approve・マージ・Issue** は GitHub の機能です。GitHub の Web サイトで行います。

---

## 変更は3つの場所を進んでいく

書いた変更が「今どこにあるか」に注目すると、分かりやすくなります。変更は、次の3つの場所を順番に進んでいきます。

```
【自分の PC】               【GitHub】                       【GitHub】
 自分の PC の履歴  ── push ──→  作業用のブランチ  ── PR → マージ ──→  main
 （commit で記録）            （feature/#8-… など）                （正式版）
                                                                  │
                                                       （mini-games では）
                                                       自動で公開URLに反映
```

| 操作 | やること | 変更がある場所 | 相方から見えるか |
| --- | --- | --- | --- |
| commit | 変更に名前（メッセージ）をつけて、自分の PC に記録する | 自分の PC だけ | 見えない |
| push | 記録した変更を GitHub のブランチに送る | GitHub の作業用のブランチ | 見える（まだ main ではない） |
| PR → マージ | 相方に確認してもらい、main に入れる | GitHub の main | 正式版に入る。mini-games では公開URLにも反映される |

## コミット・push・プルリクエストの違い

### commit（コミット）：自分の PC に記録する

- 「ここまでの変更」を、メッセージ付きで1件の記録にします（例：`feat: じゃんけんの勝ち負けを判定する`）。
- 記録は**自分の PC の中だけ**にあります。GitHub にも、相方の PC にも出ません。
- 何回でもできます。前のコミットに戻ることもできます。
- コミットの前に `git add`（VS Code では「＋」）で、どのファイルを記録に入れるかを選びます。

### push（プッシュ）：GitHub に送る

- 自分の PC のコミットを、GitHub の**同じ名前のブランチ**に送ります。
- push すると、PC が壊れても記録が消えず、相方も GitHub で見られるようになります。
- 送り先は作業用のブランチ（`feature/#8-…` など）なので、**push しても main は変わりません**。

### プルリクエスト（PR）：main に入れてほしいとお願いする

- 「このブランチの変更を main に入れたいので、見てください」というお願いです。**GitHub の Web サイトで作ります**（コマンドではありません）。
- PR を出すと、次のことが起きます。
  1. CI（GitHub Actions の `check`）が自動で動き、lint・テスト・ビルドを確かめる
  2. 相方が変更を読んでコメントし、問題なければ Approve する
  3. Approve されたら、PR を出した本人が「Merge pull request」を押す
  4. ここで初めて main に変更が入る（mini-games では Deploy が動き、公開URLにも反映される）

## ゲームのセーブにたとえると

| 操作 | たとえ |
| --- | --- |
| commit | **セーブ**。今の状態を自分のゲーム機に保存する。何回でもでき、前のセーブに戻れる。ただし自分のゲーム機の中だけ |
| push | セーブデータを**クラウドに上げる**。ゲーム機が壊れても消えず、相方も見られる |
| PR | 「このセーブデータを、チーム共通の本番データに入れていいですか？」と相方に**頼む** |
| マージ | 相方が OK を出したので、**本番データに入れる** |

## 実際の流れ

例：Issue #8 の作業をするとき

```
1. main を最新にして、ブランチを作る        … git switch main → git pull → git switch -c "feature/#8-janken-logic"
2. main.js などを書いて保存する             … ファイルを変えただけ（まだ記録していない）
3. git add . → git commit -m "feat: …"    … commit：自分の PC に記録
4. （必要なら 2〜3 を何回か繰り返す）
5. git push -u origin "feature/#8-janken-logic"  … push：GitHub のブランチに送る
6. GitHub で「Compare & pull request」を押す  … PR：main に入れてとお願い
7. 相方がレビューして Approve
8. 自分が「Merge pull request」を押す         … ここで初めて main に入る
9. 手元を main に戻して git pull            … マージ後の main を自分の PC に取り込む
```

**画面で確かめてみる**

| いつ | GitHub の画面 |
| --- | --- |
| commit した直後 | 何も変わらない（まだ自分の PC の中だけ） |
| push した後 | ブランチの一覧に自分のブランチが出て、コミットが見える。main は変わらない |
| PR を出した後 | 「Pull requests」タブに PR が出て、CI が動く |
| マージした後 | main のファイルが変わる |

## pull（プル）

push の**反対向き**の操作です。GitHub の最新の変更を、自分の PC に取り込みます。

| 操作 | 向き |
| --- | --- |
| push | 自分の PC → GitHub |
| pull | GitHub → 自分の PC |

- 相方の PR がマージされても、自分の PC の main は自動では変わりません。`git pull` して初めて取り込まれます。
- そのため、**ブランチを作る前に必ず main を pull** します。古い main から作ると、相方の変更が入っていない状態で作業することになります。
- 名前が似ていますが、**pull とプルリクエストは別のもの**です。プルリクエストは「私の変更を取り込んで（pull して）ください」というお願い、という意味からきています。

## なぜ main に直接 push しないのか

main はルールセット「protect-main」で守られていて、直接 push できません。変更は必ず PR を通します。

- 間違ったコードが、いきなり正式版（mini-games では公開中のサイト）に入らない
- CI と相方の2つのチェックを必ず通る
- 「何のために、何を変えたか」が PR に残り、あとから見返せる
- 2人が同時に作業しても、それぞれのブランチで進めるので、相手の作業を壊さない

実際の開発現場でも、同じやり方が使われています。

## よくある疑問

- **commit しただけで GitHub に出る？**
  出ません。push するまでは自分の PC の中だけです。
- **push したら main に入る？**
  入りません。push の送り先は作業用のブランチです。main に入るのは、PR がマージされたときだけです。
- **PR はコマンドで作るの？**
  いいえ。PR は GitHub の機能なので、GitHub の Web サイト（または VS Code の拡張機能 GitHub Pull Requests）で作ります。commit と push は Git の機能です。
- **PR を出した後に、レビューで直しを頼まれたら？**
  同じブランチで直して commit し、もう一度 push します。同じ PR に自動で追加されるので、PR を出し直す必要はありません。ただし、Approve された後に push すると承認が取り消されるので、もう一度 Approve してもらいます。
- **commit はどのくらいの単位でするの？**
  「1つのまとまった変更」ごとです。たとえば「判定の関数を追加」「テストを追加」のように、メッセージ1行で説明できる単位にすると、あとから見返しやすくなります。
- **push を忘れたらどうなる？**
  相方からも GitHub からも見えないままです。PR も作れません。commit したら、区切りのいいところで push しましょう。
